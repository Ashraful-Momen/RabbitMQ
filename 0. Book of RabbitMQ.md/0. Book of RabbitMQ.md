## 1. RabbitMQ কী? | What is RabbitMQ?

### 🇧🇩 বাংলায়

**RabbitMQ** হলো একটি ওপেন-সোর্স **Message Broker** সফটওয়্যার, যা **AMQP (Advanced Message Queuing Protocol)** প্রোটোকল ব্যবহার করে। এটি বিভিন্ন অ্যাপ্লিকেশন বা মাইক্রোসার্ভিসের মধ্যে **অ্যাসিঙ্ক্রোনাস (asynchronous)** মেসেজ পাঠানো-গ্রহণের ব্যবস্থা করে।

**সহজ ভাষায় (রেস্টুরেন্টের উদাহরণ):**

- 🧑 **Customer (Producer)** = অর্ডার দেয়
- 🧑‍🍳 **Waiter (RabbitMQ)** = অর্ডার নিয়ে রান্নাঘরে পৌঁছায়
- 👨‍🍳 **Chef (Consumer)** = অর্ডার রান্না করে

RabbitMQ হলো সেই **Waiter** — যে নিশ্চিত করে অর্ডার সঠিকভাবে পৌঁছেছে, হারায়নি, আর Chef ফ্রি হলেই কাজ পাবে।

### 🇬🇧 In English

RabbitMQ is an open-source **message broker** implementing the **AMQP** protocol. It lets distributed systems communicate **asynchronously**: one service sends a message, another receives it later — with no direct dependency between them.

### কেন প্রোডাকশনে RabbitMQ? | Why RabbitMQ in Production?

| সমস্যা (Problem) | RabbitMQ সমাধান (Solution) |
|---|---|
| Tight Coupling — সার্ভিসগুলো একে অপরকে চেনে | Producer/Consumer শুধু Exchange/Queue চেনে |
| Synchronous Bottleneck — ধীর রেসপন্স | Async কমিউনিকেশন → দ্রুত API রেসপন্স |
| Heavy Tasks — ইমেইল, রিপোর্ট, ইমেজ প্রসেসিং | Worker Queue দিয়ে ব্যাকগ্রাউন্ডে অফলোড |
| Failures — সার্ভিস ডাউন হলে মেসেজ লস | Queue-এ সেভ থাকে, Consumer ফিরলেই প্রসেস |
| Scalability — লোড বাড়লে | শুধু নতুন Consumer যোগ করুন (horizontal scaling) |

**মূল সুবিধা (Key Benefits):** Asynchronous Processing • Loose Coupling • Load Balancing • Message Persistence • High Availability

## 2. মূল উপাদানসমূহ | Core Components

```
┌─────────────┐      ┌──────────────┐      ┌─────────┐      ┌─────────────┐
│  Producer   │─────►│   Exchange   │─────►│  Queue  │─────►│  Consumer   │
│ (প্রোডিউসার) │      │  (এক্সচেঞ্জ)   │      │  (কিউ)   │      │ (কনজিউমার)   │
└─────────────┘      └──────────────┘      └─────────┘      └─────────────┘
   অর্ডার পাঠায়          রুট করে             জমা রাখে           প্রসেস করে
```

### ✅ Producer (প্রোডিউসার)
যে অ্যাপ মেসেজ **পাঠায়**। মনে রাখুন: Producer সরাসরি Queue-তে পাঠায় না — **Exchange**-এ পাঠায়।
*The app that sends messages. It never sends directly to a queue — always to an exchange.*

### ✅ Exchange (এক্সচেঞ্জ)
একটি **রাউটিং এজেন্ট** — Producer থেকে মেসেজ নিয়ে রুল অনুযায়ী সঠিক Queue-তে পাঠায়। Exchange-এর **নিজের কোনো স্টোরেজ নেই**।
*A routing agent with no storage — it only routes messages to queues.*

### ✅ Queue (কিউ)
মেসেজ এখানে **স্টোর** হয় যতক্ষণ না Consumer নেয়। **FIFO** (First In, First Out) অর্ডারে কাজ করে।
*A buffer storing messages in FIFO order until a consumer takes them.*

### ✅ Consumer (কনজিউমার)
Queue থেকে মেসেজ **পড়ে ও প্রসেস** করে, তারপর **ACK** পাঠায় — তখন RabbitMQ মেসেজটি ডিলিট করে।
*Reads and processes messages, then sends an acknowledgment (ACK).*

### ✅ Binding (বাইন্ডিং)
Exchange আর Queue-এর মধ্যে **সংযোগ + রাউটিং রুল**।
*The link between an exchange and a queue, with routing rules.*

### ✅ Routing Key (রাউটিং কী)
মেসেজের একটি অ্যাট্রিবিউট — Exchange এটি দেখে সিদ্ধান্ত নেয় মেসেজ কোন Queue-তে যাবে।
*A message attribute the exchange uses to decide the destination queue.*

### ✅ Virtual Host (vhost)
লজিক্যাল আলাদা এনভায়রনমেন্ট — একই সার্ভারে একাধিক প্রজেক্ট আইসোলেটেড রাখতে।
*Logical isolation — separate namespaces per project/team on one server.*

## 3. Exchange Types | ৪ ধরনের এক্সচেঞ্জ

### 1️⃣ Direct Exchange — হুবহু ম্যাচ (Exact Match)

Routing Key **হুবহু মিললেই** মেসেজ Queue-তে যাবে।

```
Producer ──["order.new"]──► Exchange ──["order.new"]──► Queue A ✓
                                └──["order.old"]──► Queue B ✗
```

**ব্যবহার | Use case:** নির্দিষ্ট টাস্ক নির্দিষ্ট ওয়ার্কারে — `order.created`, `payment.failed`

### 2️⃣ Fanout Exchange — ব্রডকাস্ট (সবার কাছে)

**সব বাউন্ড Queue-তে** মেসেজের কপি যায়। Routing Key সম্পূর্ণ **ইগনোর** করে।

```
                    ┌──► Queue 1 (Email)
Producer ──► Exchange ├──► Queue 2 (SMS)
                    └──► Queue 3 (Push)
```

**ব্যবহার | Use case:** Pub/Sub — নোটিফিকেশন, লগ ব্রডকাস্ট, সিস্টেম অ্যানাউন্সমেন্ট। শুধু Queue নামই যথেষ্ট, route_key দরকার নেই।

### 3️⃣ Topic Exchange — প্যাটার্ন ম্যাচিং (Wildcard)

Wildcard দিয়ে Routing Key ম্যাচ করে: **`*`** = ঠিক ১টি শব্দ, **`#`** = ০ বা ততোধিক শব্দ।

```
routing_key = "order.new.urgent"
    ├──► Queue A [pattern: "order.#"]   ✓
    ├──► Queue B [pattern: "*.urgent"]  ✗ (order.new.urgent = 3 শব্দ)
    └──► Queue C [pattern: "email.*"]   ✗
```

**ব্যবহার | Use case:** ক্যাটাগরি-ভিত্তিক ফিল্টারিং — `order.*`, `#.error`, `user.#`। মাইক্রোসার্ভিসে সবচেয়ে ফ্লেক্সিবল।

### 4️⃣ Headers Exchange — মেটাডেটা ভিত্তিক

Routing Key নয়, মেসেজের **header অ্যাট্রিবিউট** দিয়ে রাউটিং। Binding-এ `x-match: all` (সব হেডার মিলতে হবে) অথবা `x-match: any` (যেকোনো একটা মিললেই)।

```
headers = {"type": "order", "priority": "high"}
```

**ব্যবহার | Use case:** জটিল মাল্টি-অ্যাট্রিবিউট রাউটিং (কম ব্যবহৃত)।

### 📊 এক নজরে তুলনা | Quick Comparison

| Type | Routing Logic | Routing Key? | ব্যবহার |
|---|---|---|---|
| **Direct** | Exact match | ✅ দরকার | নির্দিষ্ট টাস্ক → নির্দিষ্ট ওয়ার্কার |
| **Fanout** | Broadcast to all | ❌ ইগনোর করে | Pub/Sub, নোটিফিকেশন |
| **Topic** | Wildcard (`*`, `#`) | ✅ pattern হিসেবে | ফ্লেক্সিবল ইভেন্ট রাউটিং |
| **Headers** | Header attributes | ❌ হেডার দরকার | জটিল মেটাডেটা রাউটিং |

## 4. ইনস্টলেশন ও সেটআপ | Installation & Setup

### 🐳 Docker দিয়ে (সবচেয়ে সহজ | Easiest — Recommended)

```bash
docker run -d \
  --name rabbitmq \
  -p 5672:5672 \
  -p 15672:15672 \
  -e RABBITMQ_DEFAULT_USER=admin \
  -e RABBITMQ_DEFAULT_PASS=secret \
  rabbitmq:3-management
```

| Port | কাজ | Purpose |
|---|---|---|
| **5672** | AMQP প্রোটোকল — Producer/Consumer কানেকশন | AMQP protocol — client connections |
| **15672** | Management Web UI | Web dashboard |
| **5671** | AMQP over TLS (প্রোডাকশন) | Secure AMQP (production) |

> 🔑 **Management UI:** http://localhost:15672 → user: `admin`, pass: `secret` (Docker env অনুযায়ী) অথবা ডিফল্ট `guest`/`guest`

> ⚠️ **গুরুত্বপূর্ণ টিপ (from my notes correction):** AMQP সার্ভার চলে **5672** পোর্টে, কিন্তু **Dashboard চলে 15672** পোর্টে! ব্রাউজারে `localhost:5672` খুললে কাজ করবে না — সবসময় `localhost:15672` ব্যবহার করুন।
> *The AMQP server runs on 5672, but the dashboard is on 15672 — a very common beginner mistake.*

### 🐧 Ubuntu/Debian (APT দিয়ে)

```bash
sudo apt update
sudo apt install rabbitmq-server -y
sudo systemctl enable rabbitmq-server
sudo systemctl start rabbitmq-server

# Management Plugin চালু করুন | Enable management plugin
sudo rabbitmq-plugins enable rabbitmq_management
```

> ⚠️ **ডিফল্ট `guest` ইউজার শুধু localhost থেকে কাজ করে!** রিমোট অ্যাক্সেসের জন্য নতুন ইউজার বানান:
> *The default guest user only works from localhost. Create a new user for remote access:*

```bash
sudo rabbitmqctl add_user myuser mypass
sudo rabbitmqctl set_user_tags myuser administrator
sudo rabbitmqctl set_permissions -p / myuser ".*" ".*" ".*"
```

### 📄 কনফিগারেশন ফাইল | Config File — `/etc/rabbitmq/rabbitmq.conf`

```ini
# নেটওয়ার্ক | Network
listeners.tcp.default = 5672
management.tcp.port = 15672

# ডিফল্ট vhost
default_vhost = /

# ডিস্ক ফ্রি লিমিট — কম হলে মেসেজ গ্রহণ বন্ধ করবে | Stops accepting messages if disk is low
disk_free_limit.absolute = 2GB

# মেসেজ TTL — ১ ঘণ্টা পর অটো ডিলিট | Default message TTL
queue.default_message_ttl = 3600000
```

## 5. Management Dashboard | ব্রাউজার দিয়ে সব কাজ

ব্রাউজারে যান: **http://localhost:15672** (guest/guest)। Dashboard-এ পাবেন:

- **Overview** — মেসেজ রেট, কানেকশন, চ্যানেল
- **Exchanges** — এক্সচেঞ্জ তৈরি, Queue বাইন্ড/আনবাইন্ড, মেসেজ পাবলিশ
- **Queues** — কিউ তৈরি, মেসেজ কাউন্ট, Get Message
- **Admin** — ইউজার, vhost, পারমিশন, পলিসি

### Exchange তৈরি ও Binding (Dashboard থেকে)

1. **Exchanges ট্যাব → Add a new exchange** → নাম দিন (যেমন: `myexchange`), Type সিলেক্ট করুন
2. এক্সচেঞ্জের নামে **ক্লিক** করুন → **Bindings** সেকশনে:
   - **To queue:** কিউ সিলেক্ট করুন (যেমন: `password-reset`)
   - **Routing key:** দিন (যেমন: `innovative-password-reset`)
   - **Arguments:** (অপশনাল)
3. একই জায়গা থেকে **Unbind**ও করা যায়

### মেসেজ পাবলিশ (Dashboard থেকে)

Exchange পেজের **Publish message** সেকশনে:
1. **Routing key** — সেট করুন
2. **Headers** — সেট করুন (Headers exchange হলে)
3. **Properties** — delivery_mode ইত্যাদি
4. **Payload** — মেসেজ লিখুন → **Publish message**

### মেসেজ দেখা | Reading Messages

**Queues ট্যাব → কিউতে ক্লিক → Get Message(s)** সেকশনে মেসেজ দেখুন। মেসেজ কাউন্ট (Ready/Unacked/Total) কিউ লিস্টেই দেখা যায়।

> 💡 **টিপ:** Dashboard থেকে Get Message করলে ডিফল্টে মেসেজ **requeue** হয়ে যায় (হারায় না)। `ack_requeue_false` সিলেক্ট করলে মেসেজ স্থায়ীভাবে সরে যাবে — সাবধানে!

## 6. Queue সেটআপ বিস্তারিত | Queue Setup in Detail

Dashboard → Queues → **Add a new queue** করলে যে অপশনগুলো পাবেন:

### 1. Virtual Host
কোন vhost-এ কিউ হবে। dev/staging/production আলাদা রাখতে vhost ব্যবহার করুন।

### 2. Type — কিউ টাইপ (খুবই গুরুত্বপূর্ণ!)

| Type | কবে ব্যবহার করবেন | When to use |
|---|---|---|
| **Classic** | সাধারণ ব্যবহারের ডিফল্ট | General purpose (default) |
| **Quorum** | **High Availability** দরকার — ডেটা লস মানা যাবে না (যেমন: পেমেন্ট) | Critical data — replicated across nodes |
| **Stream** | হাই-থ্রুপুট স্ট্রিমিং, রিয়েল-টাইম অ্যানালিটিক্স, লগ প্রসেসিং | High-throughput streaming |

> 💡 **From my notes:** পেমেন্ট/ক্রিটিক্যাল সিস্টেমে **Quorum**, স্ট্রিমিংয়ে **Stream**, বাকি সব জায়গায় **Classic**।

### 3. Name
কিউর নাম। **Best practice:** কিউর নামই routing key হিসেবে রাখুন (যেমন: `order_processing_queue`) — মনে রাখা সহজ।

### 4. Durability — সবচেয়ে গুরুত্বপূর্ণ সিদ্ধান্ত!

| Option | মানে | Meaning |
|---|---|---|
| **Durable** | সার্ভার রিস্টার্ট হলেও কিউ **টিকে থাকবে** ✅ | Survives broker restart |
| **Transient** | রিস্টার্টে সব **হারিয়ে যাবে** ❌ | Lost on restart |

> ⚠️ **Production রুল:** সবসময় **Durable** + message-এ `delivery_mode=2` (persistent)। শুধু durable queue যথেষ্ট নয় — **মেসেজও persistent হতে হবে!**

### 5. Arguments — অ্যাডভান্সড টিউনিং

| Argument | কাজ | Purpose |
|---|---|---|
| `x-max-priority` | Priority queue চালু (যেমন: 10) | Enable priorities |
| `x-message-ttl` | মেসেজের মেয়াদ (ms) — মেয়াদে শেষে ডিলিট/DLX | Message expiry |
| `x-dead-letter-exchange` | ব্যর্থ মেসেজ কোন exchange-এ যাবে | Dead letter routing |
| `x-max-length` | কিউতে সর্বোচ্চ কতগুলো মেসেজ | Queue length cap |
| `x-queue-mode: lazy` | ডিস্ক-বেসড স্টোরেজ (বড় ব্যাকলগ) | Disk-based storage |

```python
import pika
import json

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

channel.exchange_declare(exchange='order_exchange', exchange_type='direct', durable=True)
channel.queue_declare(queue='new_orders', durable=True)
channel.queue_bind(exchange='order_exchange', queue='new_orders', routing_key='order.new')

def process_order(ch, method, properties, body):
    order = json.loads(body)
    print(f"📦 নতুন অর্ডার: {order['order_id']} — {order['customer_name']}")
    try:
        # ... বিজনেস লজিক | business logic ...
        ch.basic_ack(delivery_tag=method.delivery_tag)     # সফল → ACK
        print("✅ প্রসেস সম্পন্ন")

channel.basic_qos(prefetch_count=1)   # একসাথে ১টা মেসেজ | one message at a time
channel.basic_consume(queue='new_orders', on_message_callback=process_order)

channel.start_consuming()
```

### 📥 Consumer (PHP)

```php
<?php
require_once __DIR__ . '/vendor/autoload.php';

use PhpAmqpLib\Connection\AMQPStreamConnection;

$connection = new AMQPStreamConnection('localhost', 5672, 'admin', 'secret');
$channel = $connection->channel();

$channel->exchange_declare('order_exchange', 'direct', false, true, false);
$channel->queue_declare('new_orders', false, true, false, false);
$channel->queue_bind('new_orders', 'order_exchange', 'order.new');

echo "⏳ অর্ডারের জন্য অপেক্ষা করছি...\n";

$callback = function ($msg) {
    $order = json_decode($msg->body, true);
    echo "📦 নতুন অর্ডার: {$order['order_id']} — {$order['customer_name']}\n";

    try {
        // processOrder($order);  // বিজনেস লজিক
        $msg->ack();   // সফল → ACK
        echo "✅ প্রসেস সম্পন্ন\n";
    } catch (Exception $e) {
        echo "❌ এরর: " . $e->getMessage() . "\n";
        $msg->nack(false, false);   // (multiple=false, requeue=false) → DLQ-তে
    }
};

$channel->basic_qos(null, 1, null);   // prefetch = 1
$channel->basic_consume('new_orders', '', false, false, false, false, $callback);

while ($channel->is_consuming()) {
    $channel->wait();
}

$channel->close();
$connection->close();
```

> ⚠️ **দুটি জীবন-রক্ষাকারী রুল (from my notes):**
> 1. **`no_ack = false`** রাখুন এবং সফল হলেই `$msg->ack()` — নাহলে ক্র্যাশে মেসেজ হারাবে।
> 2. **`nack(requeue=false)`** — নাহলে ফেইলড মেসেজ আবার কিউতে ঢুকে **ইনফিনিট লুপ** তৈরি করবে!

### 🐍↔️🐘 Python vs PHP চিটশিট

| কাজ | Python (pika) | PHP (php-amqplib) |

| Exchange | `channel.exchange_declare(...)` | `$channel->exchange_declare(...)` |
| পাবলিশ | `channel.basic_publish(...)` | `$channel->basic_publish($msg, ...)` |
| কনজিউম | `channel.basic_consume(...)` | `$channel->basic_consume(...)` |
| ACK | `ch.basic_ack(delivery_tag=...)` | `$msg->ack()` |
| NACK | `ch.basic_nack(..., requeue=False)` | `$msg->nack(false, false)` |

## 11. Messaging Patterns | Pub/Sub, Worker, Routing

### 🏭 Pattern 1: Worker Queue (Task Distribution) — লোড ব্যালেন্সিং

একাধিক Consumer **একই Queue** থেকে নেয় → RabbitMQ **Round-Robin**-এ ভাগ করে দেয়।

```
                 ┌──► Worker 1
Producer ──► Queue ──┼──► Worker 2
                 └──► Worker 3
```

**ব্যবহার:** ইমেইল সেন্ডিং, ইমেজ প্রসেসিং, পেমেন্ট ভেরিফিকেশন — ভারী কাজ ব্যাকগ্রাউন্ডে।

**সমস্যা:** Round-Robin ধীর ওয়ার্কারকেও সমান কাজ দেয়।
**সমাধান — Fair Dispatch (QoS):**

```python
channel.basic_qos(prefetch_count=1)   # একটা শেষ না হলে নতুনটা দেবে না
```

> 💡 `prefetch_count=1` মানে: একজন Consumer একসাথে ১টার বেশি unacknowledged মেসেজ পাবে না। ব্যস্ত ওয়ার্কারকে স্কিপ করে ফ্রি ওয়ার্কারকে মেসেজ যায়। **এটাই Horizontal Scaling + Fault Tolerance-এর চাবিকাঠি।**

### 📡 Pattern 2: Publish/Subscribe (Fanout) — ব্রডকাস্ট

এক মেসেজ → **সব সাবস্ক্রাইবারে** আলাদা কপি।

**Python Producer:**
```python
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

channel.exchange_declare(exchange='logs', exchange_type='fanout')

channel.basic_publish(
    exchange='logs',
    routing_key='',                       # fanout-এ দরকার নেই
    body='সিস্টেম মেইন্টেনেন্স: আজ রাত ১০টায়'
)
print("✅ ব্রডকাস্ট সম্পন্ন")
connection.close()
```

**Python Subscriber:**
```python
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

channel.exchange_declare(exchange='logs', exchange_type='fanout')

# টেম্পোরারি, এক্সক্লুসিভ কিউ (সার্ভার নিজে নাম দেয়)
result = channel.queue_declare(queue='', exclusive=True)
queue_name = result.method.queue

channel.queue_bind(exchange='logs', queue=queue_name)

channel.basic_consume(
    queue=queue_name,
    on_message_callback=lambda ch, m, p, b: print(f"📩 {b.decode()}"),
    auto_ack=True
)
channel.start_consuming()
```

> 🧠 **মনে রাখুন:** Pub/Sub-এ প্রতিটা সাবস্ক্রাইবারের **নিজস্ব কিউ** থাকে — Exchange শুধু কপি বিলি করে।

### 🎯 Pattern 3: Topic Routing — প্যাটার্ন ভিত্তিক

```python
channel.exchange_declare(exchange='logs', exchange_type='topic')

channel.queue_declare(queue='error_logs')
channel.queue_declare(queue='all_logs')

channel.queue_bind(exchange='logs', queue='error_logs', routing_key='*.error')
channel.queue_bind(exchange='logs', queue='all_logs',   routing_key='#')

logs = [
    ('system.error',   'সিস্টেম এরর ঘটেছে'),
    ('database.error', 'ডাটাবেস সংযোগ ব্যর্থ'),
    ('system.info',    'সিস্টেম চালু হয়েছে'),
]

for routing_key, message in logs:
    channel.basic_publish(exchange='logs', routing_key=routing_key, body=message)
```

- `system.error` → **দুই কিউতেই** যাবে (`*.error` + `#`)
- `system.info` → শুধু `all_logs`-এ

**Wildcard রুল:** `*` = ঠিক ১ শব্দ • `#` = ০ বা বেশি শব্দ

## 12. Microservices Architecture এ RabbitMQ

### সমস্যা → সমাধান ম্যাপিং

| মাইক্রোসার্ভিস সমস্যা | RabbitMQ সমাধান |
|---|---|
| Tight Coupling | Producer/Consumer একে অপরকে চেনে না |
| Synchronous Bottleneck | Async → API দ্রুত রেসপন্ড করে |
| Failures & Retries | DLX + Retry Queue |
| Scalability | Worker Queue-তে Consumer যোগ করুন |
| Event-Driven Design | Fanout/Topic Exchange দিয়ে ইভেন্ট ব্রডকাস্ট |

### 🛒 বাস্তব উদাহরণ: Order Processing System

```
Order Service (Producer)
    │ routing_key: "order.created"
    ▼
Topic Exchange: "order_events"
    │
    ├──► payment_queue  ──► Payment Service   [binding: order.created]
    ├──► inventory_queue ──► Inventory Service [binding: order.created]
    └──► analytics_queue ──► Analytics Service [binding: order.#]
```

**Producer (Order Service):**
```python
import pika, json

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

channel.exchange_declare(exchange='order_events', exchange_type='topic', durable=True)

order_data = {"order_id": 123, "user_id": 456, "items": ["item1", "item2"]}

channel.basic_publish(
    exchange='order_events',
    routing_key='order.created',
    body=json.dumps(order_data),
    properties=pika.BasicProperties(delivery_mode=2)
)
connection.close()
```

**Consumer (Payment Service):**
```python
import pika, json

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

channel.exchange_declare(exchange='order_events', exchange_type='topic', durable=True)
channel.queue_declare(queue='payment_queue', durable=True)
channel.queue_bind(exchange='order_events', queue='payment_queue', routing_key='order.created')

def callback(ch, method, properties, body):
    order = json.loads(body)
    print(f"💳 Processing payment for order {order['order_id']}")
    ch.basic_ack(delivery_tag=method.delivery_tag)

channel.basic_qos(prefetch_count=1)
channel.basic_consume(queue='payment_queue', on_message_callback=callback)
channel.start_consuming()
```

### 🔗 Correlation ID — রিকোয়েস্ট/রেসপন্স ট্র্যাকিং

মাইক্রোসার্ভিসে RPC-স্টাইল কলে প্রতিটা মেসেজে `correlation_id` রাখুন:

```php
$message = [
    'source'         => 'service_a',
    'action'         => 'process_data',
    'data'           => $data,
    'timestamp'      => time(),
    'correlation_id' => uniqid()   // রেসপন্স ম্যাচ করার জন্য
];
```

### 🏅 Best Practices (সেরা অনুশীলন)

1. **Idempotent Consumers** — একই মেসেজ দুইবার প্রসেস হলেও সিস্টেম না ভাঙে (যেমন: প্রসেসের আগে চেক করুন `order_id` আগে প্রসেস হয়েছে কিনা)
2. **Meaningful Routing Keys** — `order.created.v1`, `user.profile.updated` (verb past tense-এ)
3. **Message = Data, not Commands** — ইভেন্ট-স্টাইল মেসেজ পাঠান
4. **Small Payloads** — বড় ডেটা হলে রেফারেন্স (ID/URL) পাঠান, পুরো ডেটা নয়
5. **প্রতি সার্ভিসে আলাদা vhost/user** — আইসোলেশন ও নিরাপত্তা

## 13. ACK, NACK ও Retry Logic | মেসেজ নিশ্চিতকরণ

### কেন ACK দরকার?

`auto_ack=True` হলে মেসেজ পাওয়া মাত্রই ডিলিট হয়ে যায় — Consumer ক্র্যাশ করলে **মেসেজ হারিয়ে যাবে**।
Manual ACK-এ: Consumer প্রসেস শেষে ACK পাঠায়; ক্র্যাশ করলে RabbitMQ মেসেজটি **অন্য Consumer-কে দিয়ে দেয়**।

```
Consumer মেসেজ পেলো ──► প্রসেস করলো ──► সফল? ──► ACK ──► মেসেজ ডিলিট ✅
                            │
                            └── ক্র্যাশ/ফেইল ──► NACK ──► requeue বা DLQ 🔄
```

### সঠিক ACK/NACK প্যাটার্ন (Python)

```python
def callback(ch, method, properties, body):
    try:
        process_message(body)
        ch.basic_ack(delivery_tag=method.delivery_tag)          # ✅ সফল
        print("✅ ACK পাঠানো হয়েছে")
    except Exception as e:
        ch.basic_nack(
            delivery_tag=method.delivery_tag,
            requeue=False                                       # DLQ-তে যাবে
        )
        print(f"❌ NACK: {e}")
```

### 🔄 স্মার্ট Retry Logic — মেসেজের ভেতরে কাউন্টার

```python
def callback_with_retry(ch, method, properties, body):
    message = json.loads(body)
    retry_count = message.get('retry_count', 0)
    max_retries = 3

    try:
        process_order(message)
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except Exception as e:
        if retry_count < max_retries:
            message['retry_count'] = retry_count + 1
            # নতুন মেসেজ হিসেবে আবার পাবলিশ
            ch.basic_publish(
                exchange='',
                routing_key='order_queue',
                body=json.dumps(message)
            )
            print(f"🔄 Retry {retry_count + 1}/{max_retries}")
            ch.basic_ack(delivery_tag=method.delivery_tag)   # পুরনোটা ACK
        else:
            print("❌ Max retries শেষ — DLQ-তে পাঠানো হচ্ছে")
            ch.basic_nack(delivery_tag=method.delivery_tag, requeue=False)
```

> ⚠️ **কখনোই `requeue=True` ব্লাইন্ডলি ব্যবহার করবেন না** — একই ত্রুটিপূর্ণ মেসেজ বারবার ফিরে এসে **infinite loop** তৈরি করবে (poison message)। সাময়িক এররে (DB down) requeue, স্থায়ী এররে (invalid data) DLQ।

## 14. Dead Letter Exchange (DLX) | ব্যর্থ মেসেজের সেফটি নেট

কোনো মেসেজ **Dead** হয় যখন:
- Consumer **NACK/reject** করে (`requeue=false`)
- **TTL শেষ** হয়ে যায়
- Queue-র **max-length** অতিক্রম করে

তখন মেসেজটি ডিলিট না হয়ে **DLX (Dead Letter Exchange)**-এ চলে যায় → সেখানকার **DLQ (Dead Letter Queue)**-এ জমা থাকে → পরে ম্যানুয়ালি ঘেঁটে দেখা বা রি-প্রসেস করা যায়।

```
main_orders Queue ──[ফেইল / TTL শেষ / ওভারফ্লো]──► DLX ──► failed_orders (DLQ)
                                                              │
                                                              ▼
                                                     Manual Review / Retry / Alert
```

### Python দিয়ে DLX সেটআপ

```python
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

# 1. DLX + DLQ তৈরি
channel.exchange_declare(exchange='dlx', exchange_type='fanout', durable=True)
channel.queue_declare(queue='failed_orders', durable=True)
channel.queue_bind(exchange='dlx', queue='failed_orders')

# 2. Main queue-এ DLX arguments
channel.queue_declare(
    queue='main_orders',
    durable=True,
    arguments={
        'x-dead-letter-exchange': 'dlx',   # ব্যর্থ মেসেজ এখানে যাবে
        'x-message-ttl': 300000,           # ৫ মিনিট TTL
        'x-max-length': 1000               # সর্বোচ্চ ১০০০ মেসেজ
    }
)
print("✅ DLX সেটআপ সম্পন্ন")
connection.close()
```

### PHP দিয়ে DLX সেটআপ

```php
use PhpAmqpLib\Wire\AMQPTable;

$channel->exchange_declare('dlx', 'fanout', false, true, false);
$channel->queue_declare('failed_orders', false, true, false, false);
$channel->queue_bind('failed_orders', 'dlx');

$channel->queue_declare('main_orders', false, true, false, false, false,
    new AMQPTable([
        'x-dead-letter-exchange' => 'dlx',
        'x-message-ttl' => 300000,
        'x-max-length' => 1000
    ])
);
```

### cURL দিয়ে DLX

```bash
curl -u guest:guest -H "content-type:application/json" \
 -X PUT -d '{"arguments":{"x-dead-letter-exchange":"dlx_exchange"}}' \
 http://localhost:15672/api/queues/%2f/myqueue
```

> ✅ **Production রুল:** প্রতিটা গুরুত্বপূর্ণ কিউতে DLX থাকবেই। DLQ মনিটর করুন — DLQ-তে মেসেজ জমলে অ্যালার্ট দিন।

## 15. Priority Queue ও TTL

### ⭐ Priority Queue — গুরুত্ব অনুযায়ী প্রসেসিং

কিউ তৈরির সময় `x-max-priority` দিন (০–১০ বা ০–২৫৫), মেসেজে `priority` দিন। বেশি priority আগে প্রসেস হবে।

**Python:**
```python
channel.queue_declare(
    queue='priority_orders',
    durable=True,
    arguments={'x-max-priority': 10}
)

# VIP আগে, সাধারণ পরে
messages = [
    ('VIP Customer অর্ডার', 10),
    ('সাধারণ অর্ডার', 5),
    ('নন-আর্জেন্ট অর্ডার', 1),
]
for body, priority in messages:
    channel.basic_publish(
        exchange='',
        routing_key='priority_orders',
        body=body,
        properties=pika.BasicProperties(priority=priority, delivery_mode=2)
    )
```

**প্রসেসিং অর্ডার:**
```
Queue: [P:10 VIP] → [P:5 Normal] → [P:1 Low]
        প্রথম        দ্বিতীয়         শেষ
```

> 💡 **টিপ:** `x-max-priority` বেশি রাখলে (যেমন ২৫৫) পারফরম্যান্স খরচ বাড়ে — ১০-এর মধ্যে রাখাই ভালো।

### ⏰ TTL (Time-To-Live) — মেয়াদ

দুই লেভেলে TTL দেওয়া যায়:

```python
# 1. Queue-level: সব মেসেজ ১ ঘণ্টা পর মেয়াদোত্তীর্ণ
arguments={'x-message-ttl': 3600000}

# 2. Message-level: এই মেসেজটা ৬০ সেকেন্ডে মেয়াদোত্তীর্ণ
properties=pika.BasicProperties(expiration='60000')
```

TTL শেষ হলে মেসেজ ডিলিট হয় — অথবা DLX সেট থাকলে DLQ-তে যায়।

## 16. High Availability, Clustering ও Security

### 🪞 Mirrored Queues / Quorum Queues (HA Policy)

```bash
# সব কিউ সব নোডে রিপ্লিকেট হবে
rabbitmqctl set_policy ha-all ".*" '{"ha-mode":"all"}'
```

Management UI → Admin → Policies থেকেও করা যায়:
```json
{ "ha-mode": "all", "ha-sync-mode": "automatic" }
```

> 📌 **ক্লাস্টারে কমপক্ষে ৩টি নোড** (odd number) রাখুন — network partition (split-brain) হ্যান্ডল করতে।
> 📌 নতুন সেটআপে **Classic mirrored queues-এর বদলে Quorum Queues** ব্যবহার করুন — এটাই এখনকার রেকমেন্ডেড HA পদ্ধতি।

### 🔄 Multi-Host Failover (PHP উদাহরণ)

```php
class HAConnectionManager
{
    private $hosts;
    private $currentHost = 0;

    public function __construct(array $hosts) { $this->hosts = $hosts; }

    public function getConnection()
    {
        for ($i = 0; $i < count($this->hosts); $i++) {
            $host = $this->hosts[($this->currentHost + $i) % count($this->hosts)];
            try {
                $conn = new AMQPStreamConnection(
                    $host['host'], $host['port'], $host['user'], $host['password']
                );
                $this->currentHost = ($this->currentHost + $i) % count($this->hosts);
                return $conn;
            } catch (\Exception $e) { continue; }  // পরের হোস্ট ট্রাই
        }
        throw new \Exception('Unable to connect to any RabbitMQ host');
    }
}
```

### 🔐 Security Best Practices

| বিষয় | করণীয় |
|---|---|
| **ইউজার ম্যানেজমেন্ট** | `guest` ইউজার প্রোডাকশনে ডিসেবল; প্রতি সার্ভিসে আলাদা ইউজার |
| **vhost আইসোলেশন** | প্রতি প্রজেক্ট/টিমে আলাদা vhost (`/ecommerce`, `/payment`) |
| **TLS/SSL** | প্রোডাকশনে AMQP over TLS (port **5671**) |
| **ফায়ারওয়াল** | 5672/15672 শুধু ট্রাস্টেড নেটওয়ার্কে ওপেন |
| **Credentials** | `.env`-এ রাখুন, git-এ কমিট করবেন না; নিয়মিত রোটেট করুন |

### 📈 মনিটরিং

- **Management UI** — queue length, consumer count, message rates
- **Prometheus + Grafana** — `rabbitmq_exporter` দিয়ে
- **অ্যালার্ট** — queue length > 1000 হলে বা consumer = 0 হলে Slack/Email
- **লগ** — `/var/log/rabbitmq/`

## 18. Troubleshooting | সমস্যা ও সমাধান

### ❌ ব্রাউজারে Dashboard খুলছে না

**কারণ:** ভুল পোর্ট। AMQP সার্ভার 5672-এ, Dashboard **15672**-এ।
**সমাধান:** `http://localhost:15672` + management plugin চালু আছে কিনা দেখুন:
```bash
rabbitmq-plugins enable rabbitmq_management
```

### ❌ রিমোট সার্ভারে কানেক্ট হচ্ছে না (guest দিয়ে)

**কারণ:** `guest` ইউজার শুধু **localhost** থেকে কাজ করে।
**সমাধান:** নতুন ইউজার বানান (Chapter 4 দেখুন)।

### ❌ সার্ভার রিস্টার্টে সব মেসেজ হারিয়ে গেল

**কারণ:** Queue `durable` ছিল না, বা মেসেজ persistent ছিল না।
**সমাধান:** **দুটোই লাগবে** — `durable=True` queue + `delivery_mode=2` message।

### ❌ মেসেজ প্রসেস হচ্ছে না, কিউতে জমছে (backlog)

চেকলিস্ট:
1. Consumer চলছে কিনা? → Dashboard → Queues → **Consumers** কাউন্ট
2. `prefetch_count` ঠিক আছে কিনা?
3. কোনো poison message আটকে আছে কিনা? → DLQ চেক করুন
4. Consumer ধীর? → আরও Consumer ইনস্ট্যান্স যোগ করুন (scaling)

### ❌ একই মেসেজ বারবার আসছে (infinite loop)

**কারণ:** `nack(requeue=true)` অথবা অপ্রসেসযোগ্য মেসেজ (poison message)।
**সমাধান:** retry counter + max retries, তারপর `requeue=false` → DLQ।

### ❌ ক্র্যাশের পর মেসেজ ডুপ্লিকেট প্রসেস হলো

**ব্যাখ্যা:** ACK পাঠানোর আগে ক্র্যাশ → RabbitMQ মেসেজটি পুনরায় ডেলিভার করে। এটা **by design** (at-least-once delivery)।
**সমাধান:** Consumer-কে **idempotent** বানান — প্রসেসের আগে চেক করুন এই কাজ আগে হয়েছে কিনা।

### ❌ মেসেজ পাঠালাম, কিন্তু কোনো কিউতে পড়লো না

**কারণ:** Exchange-এর সাথে binding নেই বা routing key মিলছে না → মেসেজ **চুপচাপ ড্রপ** হয়ে গেছে!
**সমাধান:**
- Dashboard → Exchange → **Bindings** চেক করুন
- টেস্টের সময় publisher-এ `mandatory=true` দিন — unroutable মেসেজ ফেরত আসবে

## 19. Tips & Tricks Master Collection (আমার নোট থেকে)

### 🧠 কনসেপ্ট যা মনে রাখবেন

1. **Producer কখনো Queue-তে সরাসরি পাঠায় না** — সবসময় Exchange-এ। Exchange-এর নিজের স্টোরেজ নেই, শুধু রাউট করে।
2. **ফ্লো মুখস্থ রাখুন:** Producer → Exchange → Queue → Consumer → ACK।
3. **Fanout-এ routing key দরকার নেই** — Queue নামই যথেষ্ট, সব বাউন্ড কিউতে কপি যায়।
4. **Topic-এ wildcard:** `*` = ১ শব্দ, `#` = অনেক শব্দ।
5. **Headers exchange-এ routing key নয়, header key-value দিয়ে ম্যাচ** — binding arguments-এ `x-match: all/any`।

### ⚙️ সেটআপ টিপস

6. **পোর্ট কনফিউজন এড়ান:** AMQP = 5672, Dashboard/API = **15672**, TLS = 5671।
7. **Docker দিয়ে শুরু করুন** — `rabbitmq:3-management` ইমেজে Management UI বিল্ট-ইন।
8. **`guest` শুধু localhost-এ** — রিমোটে নতুন ইউজার + `set_permissions ".*" ".*" ".*"`।
9. **কিউর নাম = routing key** রাখলে মনে রাখা ও ডিবাগ করা সহজ।
10. **ক্রিটিক্যাল ডেটায় Quorum queue, স্ট্রিমিংয়ে Stream, বাকিতে Classic।**

### 🛡️ রিলায়েবিলিটি টিপস

11. **Durable + Persistent জুটি ভুলবেন না:** queue `durable=True` **এবং** message `delivery_mode=2` — একটা দিলে অন্যটা না দিলে রিস্টার্টে মেসেজ হারাবে।
12. **Manual ACK সবসময়** — প্রসেসিং সফল হলেই শুধু ACK।
13. **`nack(requeue=false)`** — ইনফিনিট লুপ থেকে বাঁচুন। রিট্রাই দরকার হলে মেসেজে কাউন্টার রাখুন।
14. **প্রতিটা কিউতে DLX** — মেসেজ কখনো "অদৃশ্য" হয়ে যাবে না।
15. **`prefetch_count=1`** — ধীর ওয়ার্কার বোঝা হবে না; এটাই fair dispatch।
16. **Declare idempotent** — Producer ও Consumer দুই দিকেই exchange/queue declare করে রাখুন, নিরাপদ।

### 🧪 টেস্টিং ও ডিবাগিং টিপস

17. **cURL দিয়ে দ্রুত টেস্ট** — কোড লেখার আগেই exchange→queue ফ্লো যাচাই করুন (`/api/.../publish`, `/api/.../get`)।
18. **Dashboard-এ Get Message করলে `ack_requeue_true` রাখুন** — শুধু দেখতে চাইলে যেন মেসেজ না হারায়।
19. **Queue জমে গেলে** Dashboard → Queues → Ready/Unacked/Consumers কাউন্ট দেখুন — consumer = 0 মানেই সমস্যা।
20. **rabbitmqadmin রাখুন PATH-এ** — স্ক্রিপ্টিং ও CI-তে কাজে লাগে।

### 🚀 প্রোডাকশন টিপস

21. **Laravel-এ নেটিভ queue driver ব্যবহার করুন** (`vladimir-yuldashev/laravel-queue-rabbitmq`) — ACK/retry অটো।
22. **Worker Supervisor দিয়ে চালান** — ক্র্যাশে অটো-রিস্টার্ট; `numprocs` বাড়িয়ে স্কেল করুন।
23. **প্রতি সার্ভিসে আলাদা vhost + ইউজার** — আইসোলেশন = নিরাপত্তা + সহজ ডিবাগিং।
24. **ক্লাস্টারে odd number (৩) নোড** + Quorum queues।
25. **DLQ-তে অ্যালার্ট লাগান** — ব্যর্থ মেসেজ জমলেই জানবেন, সপ্তাহ পরে নয়।

### 🌐 REST API (cURL)

```bash
# Health
curl -u guest:guest http://localhost:15672/api/overview

# Queue তৈরি
curl -u guest:guest -X PUT -H "content-type:application/json" \
  -d '{"durable":true}' http://localhost:15672/api/queues/%2f/QUEUE

# Exchange তৈরি
curl -u guest:guest -X PUT -H "content-type:application/json" \
  -d '{"type":"direct","durable":true}' http://localhost:15672/api/exchanges/%2f/EXCHANGE

# Binding
curl -u guest:guest -X POST -H "content-type:application/json" \
  -d '{"routing_key":"KEY"}' http://localhost:15672/api/bindings/%2f/e/EXCHANGE/q/QUEUE

# Publish
curl -u guest:guest -X POST -H "content-type:application/json" \
  -d '{"properties":{},"routing_key":"KEY","payload":"MSG","payload_encoding":"string"}' \
  http://localhost:15672/api/exchanges/%2f/EXCHANGE/publish

# Get messages
curl -u guest:guest -X POST -H "content-type:application/json" \
  -d '{"count":5,"ackmode":"ack_requeue_true","encoding":"auto"}' \
  http://localhost:15672/api/queues/%2f/QUEUE/get
```

### 🐍 Python (pika) এক নজরে

```python
import pika, json

conn = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
ch = conn.channel()

# Declare
ch.exchange_declare(exchange='ex', exchange_type='direct', durable=True)
ch.queue_declare(queue='q', durable=True)
ch.queue_bind(exchange='ex', queue='q', routing_key='key')

# Publish
ch.basic_publish(exchange='ex', routing_key='key', body=json.dumps(data),
    properties=pika.BasicProperties(delivery_mode=2))

# Consume
ch.basic_qos(prefetch_count=1)
ch.basic_consume(queue='q', on_message_callback=callback)  # callback-এ basic_ack
ch.start_consuming()
```

### 🐘 PHP (php-amqplib) এক নজরে

```php
use PhpAmqpLib\Connection\AMQPStreamConnection;
use PhpAmqpLib\Message\AMQPMessage;

$conn = new AMQPStreamConnection('localhost', 5672, 'guest', 'guest');
$ch = $conn->channel();

// Declare
$ch->exchange_declare('ex', 'direct', false, true, false);
$ch->queue_declare('q', false, true, false, false);
$ch->queue_bind('q', 'ex', 'key');

// Publish
$msg = new AMQPMessage(json_encode($data),
    ['delivery_mode' => AMQPMessage::DELIVERY_MODE_PERSISTENT]);
$ch->basic_publish($msg, 'ex', 'key');

// Consume
$ch->basic_qos(null, 1, null);
$ch->basic_consume('q', '', false, false, false, false, function ($msg) {
    // process...
    $msg->ack();          // or $msg->nack(false, false);
});
while ($ch->is_consuming()) { $ch->wait(); }
```
